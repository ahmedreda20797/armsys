# ARM ERP — Scoped Write Paths & Per-Route Scope Adoption (Wave 4)

Status: COMPLETE — HARD STOP at the M0.4 boundary.

## 1. Executive Summary

M0.4 extended the canonical M0.3 authorization architecture from read-scope
into write-scope. Before this milestone, every employee-linked mutation in the
system enforced **permission only**: any user holding an action permission
could mutate **any employee's** records. The central M0.4 rule — *permission to
act does not imply the right to act on every record* — is now enforced on 35
routes.

What changed:

- **One canonical write-scope guard** — `src/lib/scope/server.ts` wraps the
  EXISTING engine (`resolvePageScope` + `resolveEmployeeScope`) with its two
  DB reads; it contains zero scope logic of its own. All M0.4 routes consume
  this guard. No second engine, no per-route role checks, no client-side
  enforcement.
- **Employee PUT/DELETE/POST scoped** — target resolved before mutation;
  out-of-scope resolves as 404 identical to the missing-record body
  (anti-enumeration); org-reassignment (`orgNodeId`) changes are refused on
  the generic edit route and remain on the dedicated
  `/api/organization/employees/move` path (organization permission + audit +
  notifications).
- **All employee-linked mutations scoped** — attendance, requests
  (create/update/approve/reject/delete — deduction business rules untouched),
  biometric (clear = in-scope intersection; upload = unrestricted-only),
  travel, follow-ups, HR deductions, quality deductions, quality observations
  (create/update/delete/approve/reject), complaints and CAPA (optional-link
  rule), deduction waivers. Stored records are the authoritative employee
  relationship; body-supplied duplicates can never retarget authorization;
  reassignment targets are scope-checked too.
- **Aggregate/report read adoption** — every employee-specific monthly
  endpoint (attendance KPI/results detail+lists, HR performance factor,
  employee performance history, reports/employee-detail) enforces the same
  scope; `reports/run` applies **authorization first, then request
  selection**: `AUTHORIZED_SCOPE ∩ REQUESTED_SELECTION`.
- Fail-closed doctrine carried into writes: a write permission without a
  resolvable employee scope denies (empty set), never widens.

Verification: zero new TypeScript errors (19 pre-existing), zero new lint
problems (11,854 pre-existing), 1,046 tests with **72 new M0.4 tests** — 1,045
pass; the single failure is the documented pre-existing quality-migration env
failure. All M0.1/M0.2/M0.2.1/M0.3 suites green.

## 2. Pre-Implementation Route Audit

Every route under `src/app/api` was enumerated (89 route files) and mapped for
authentication, permission gate, resource lookup, scope resolution, mutation
and audit behavior. Findings that shaped the implementation:

1. `PUT/DELETE /api/employees/[id]` — permission only; PUT wrote the RAW body
   (including `orgNodeId`); DELETE cascaded into 8+ tables; neither resolved
   the target employee. Confirmed M0.3 finding.
2. `POST /api/employees`, `/api/employees/upload` — create/update workforce
   records with no employee-scope concept; created records are org-unassigned.
3. Attendance (`POST`, `[id]` PUT/DELETE) — employeeId from body/stored
   record; no lookups before DELETE; PUT could reassign records to any
   employee via raw body.
4. Requests (`POST`, `[id]` PATCH/PUT/DELETE) — approve path resolved the
   stored request; plain update and delete did not; the excuse→attendance
   deduction logic runs inside approve.
5. Biometric (`clear`, `upload`) — clear bulk-deletes a whole month for ALL
   employees; upload creates biometrics for sheet-matched employees AND
   CREATES new employees for unmatched names.
6. Travel / follow-ups / hr-deductions / quality (`qualityDeductions`) /
   quality-observations (+approve/reject) / complaints / capa-cases — all
   employee-linked (link optional for complaints/CAPA); `quality-observations`
   already had strong audit trails; most `[id]` routes lacked pre-mutation
   lookups; PUT whitelists included `employeeId` (reassignment).
7. `reports/waive-deduction` — employee-linked mutation gated only by
   `reports edit`, with zero employee validation.
8. Aggregates — `attendance-kpi/[month](/[employeeId])`,
   `attendance-results/[month](/[employeeId])`, `hr-performance/[month]/[employeeId]`,
   `employee-performance/[employeeId]`, `reports/employee-detail`,
   `reports/run`, `attendance-results/generate` — page-gated only.
9. `src/lib/validate-employee.ts` — pure existence/suspension validation, NO
   authorization content (audit confirmed).
10. `src/lib/reports/scope.ts` — confirmed a REQUEST-SHAPE selection mechanism
    (single/multiple/all vs. definition), zero viewer authorization — kept
    strictly separate (see §11).

## 3. Authorization Architecture Used

```
authenticateFromRequest()                     (JWT, unchanged)
    ↓
resolveEffectivePermissions()                (role ⊕ position ⊕ stored, unchanged)
    ↓
verifyPermission(request, resourcePage, action)   ← the ACTION gate (unchanged)
    ↓
resolve target employee                      (URL id → stored record, or body on create)
    ↓
resolveEmployeeScopeFromDb(viewer, 'employees', perms)   ← NEW thin loader (M0.4)
    = resolvePageScope + getAll(orgNodes, employees) + resolveEmployeeScope
    ('all' fast path: no DB read — admin/HR/quality)
    ↓
ctx.includes(targetEmployeeId)               (canonical engine, unchanged)
    ↓
authorized mutation → existing audit/event behavior (denials write NO events)
```

`src/lib/scope/server.ts` exports: `EMPLOYEE_SCOPE_PAGE_KEY` (`'employees'`),
`asScopeViewer`, `resolveEmployeeScopeFromDb`, `employeeInScope`,
`hasUnrestrictedEmployeeScope`. It is the only new module; routes call it,
never the raw engine (pinned by static tests).

**Why the employees-page entry carries the write scope:** M0.3 configured
evidence-based scopes on exactly one entry — employees (HR `'all'`, Quality
`'all'`, Manager `'subtree'`, generic fail-closed). Employee-linked records
describe an employee, so that entry IS the viewer's authorized employee set.
Resource pages keep their own permission (action) gate; no preset was changed
or broadened.

## 4. Permission vs Scope Enforcement Model

Independent axes, both must pass:

| Permission (action gate) | Scope (record gate) | Result |
|---|---|---|
| granted | target in scope | allowed |
| granted | target out of scope | denied (404 same-body / 403 on create) |
| granted | scope unresolvable | denied fail-closed (empty set) |
| denied | — | 403 (scope never consulted) |

Stock-role impact: admin/HR/quality unchanged everywhere (all resolve
'unrestricted'); managers — who hold requests/observations write presets —
are now confined to their managed subtree on those writes (the intended M0.4
rule); generic users with custom write grants fail closed until an
administrator configures their employees scope.

## 5. Employee PUT Scope Enforcement

`PUT /api/employees/[id]`: permission → `getById` (404 missing) →
`ctx.includes(id)` (404 **identical body**) → orgNodeId guard → mutate.
Client-supplied `userId/role/scope/employeeId` in the body are inert: the URL
id is the only target. **Organizational separation:** any `orgNodeId` CHANGE
via this route is refused (403, Arabic message pointing at the org page); a
no-op same-value field is ignored. Reassignment lives exclusively at
`/api/organization/employees/move` (organization page permission — admin-only
by stock preset — with config audit + manager notifications). No new
permission was invented.

## 6. Employee DELETE Scope Enforcement

`DELETE /api/employees/[id]`: permission → `getById` (404 missing — new, required
to resolve the target) → scope (404 same-body) → the pre-existing cascade
(attendance, requests, qualityDeductions, biometrics, travelDeals, followUps,
hrDeductions, complaints, CAPA related-id scrub) and `deleteRecord` run
unchanged. No hard-delete pattern was introduced; historical integrity
behavior is byte-identical.

Employee creates (`POST /api/employees`, `POST /api/employees/upload`) require
an UNRESTRICTED employee scope: a new employee is org-unassigned and thus
outside every restricted scope, so a scoped creator would produce records they
cannot see — fail-closed 403 (bulk upload also UPDATES matched employees by
code, which would let a scoped viewer overwrite out-of-scope records).

## 10. Employee-Linked Request Audit (travel / follow-ups / hr-deductions / quality / observations / complaints / capa)

All follow the same stored-relationship doctrine:

- Creates: scope-check `body.employeeId` before existence validation → 403.
- `[id]` mutations: pre-mutation lookup (404 missing — newly added where
  absent: travel, follow-ups, complaints, quality `[id]`, requests DELETE,
  attendance DELETE, capa DELETE) → scope on the STORED employeeId → 404
  same-body → mutate.
- Reassignment (`body.employeeId` differing from stored) requires the NEW
  target in scope too (attendance, requests, travel, follow-ups,
  hr-deductions, observations, complaints).
- Approvals (hr-deductions approve, observations approve/reject) are scoped
  on the stored employee; denial happens BEFORE any approval/audit event is
  written (verified: record stays `pending`).
- Optional-link rule (complaints, CAPA): an absent employee link passes on
  permission alone; a present link (stored OR incoming, including every
  `relatedEmployeeIds` entry on CAPA create/update) must be in scope.
- Quality business rules, HR deduction rules, scoring, evidence, categories,
  month-locks, approval workflow: untouched.

## 13. Resource Ownership Rules

The persisted resource is the source of truth: `[id]` mutations authorize on
the STORED `employeeId` (or link). A client-supplied `employeeId` beside a
`requestId` is ignored for authorization and cannot retarget (tested: spoofed
body employeeId on an out-of-scope request still 404s, no write occurs).
Where a route legitimately supports reassignment, the NEW target is
additionally scope-checked. Optional links (complaints/CAPA) enforce scope
only when a link exists.

## 14. Create Operation Rules

Resolve target from the request → scope-check → create, never create-then-
scope. The check runs BEFORE employee-existence validation, so an out-of-scope
target returns 403 without an existence oracle (an in-scope but nonexistent
employee still gets the pre-existing 400 validation error). Operations
targeting employees derived from other resources resolve that resource's
employee owner first. Bulk creates whose targets cannot be confined to a
scope (employee/biometric/quality uploads, workforce generation) require an
unrestricted scope.

## 15. Approval/Rejection Rules

Approval and rejection are mutations and are scoped identically: resolve
stored record → stored employeeId → scope → decide. Denied decisions return
the missing-record 404 BEFORE any status write, approval-history event, audit
event or notification is produced (pinned by tests: record remains `pending`).
Excuse-deduction side effects fire only for authorized decisions — unchanged.

## 29. Performance Impact

The guard reuses the M0.3 context shape per request: admin/HR/quality (the
majority of write-path viewers) hit the `'all'` fast path — the engine
short-circuits with EMPTY inputs, zero DB reads. Scoped viewers add two
`getAll` reads (orgNodes + employees) served by the existing TTL cache
(15 s, invalidated on writes), plus one `getById` for target resolution on
`[id]` routes (previously absent on several). No new caching layer, no
repeated org-graph loads within a request (one guard resolution per route
invocation; multi-target routes resolve the context once and test ids against
it). Month-list filtering is a linear in-memory pass over already-loaded rows.
