# M0.6 ORGANIZATION, ACCESS & REPORTING
# AUDIT & ARCHITECTURE REPORT

**Scope:** Read-only architecture audit of `arm-erp-project` (Next.js App Router + Firebase RTDB, ~481 TS/TSX source files, ~103 API route handlers). References use `file:line`. Nothing was implemented, migrated, or fixed. No code, files (other than this report), database records, Firebase data, API behavior, or UI were modified.

---

## 1. Executive Summary

ARM ERP is significantly further along the M0.6 target architecture than a typical CRUD app: **three of its six pillars already exist in canonical form**:

1. **Organization hierarchy exists** (`arm_erp/orgNodes` — generic-depth tree: company→department→team→subteam, Milestone 10) with impact-preview moves, cycle/depth/archived validation, and manager assignment per node.
2. **A single scope engine exists** (M0.3–M0.5): vocabulary in `src/config/permissions.ts`, pure resolver `src/lib/scope/index.ts`, DB guard layer `src/lib/scope/server.ts` adopted by **50 route files**, fail-closed to `'own'`, materialized employee-ID sets, ID-based resolution (no free text), anti-enumeration 404 semantics.
3. **A unified reporting architecture exists** (Milestone 8): declarative `ReportDefinition` contract + registry + runner pattern + authorization-first execution (`src/lib/reports/*`) — but only **one report is registered** (quality-deductions reference report), so coverage of other domains is still legacy/scattered.
4. **A shared TimeScope contract exists** (`src/lib/time-scope/index.ts`, Milestone 4): 9 scope kinds, `MetricResult` provenance, Employee-360 current/history/career layering helpers — consumption is partial.

The three structural gaps that M0.6's future phases must address:

- **Employees have no lifecycle**: no status field, no email/userId reverse link, free-text `department`/`position` snapshots are never synced with `orgNodeId`. "Active/inactive/archived" simply cannot be expressed today.
- **Reportability is uneven**: legacy parallel reporting endpoints (`/api/reports/generate|export|employee-detail|capa*`), page-local computations, and one registered unified report coexist. Migration into the registry+runner model is the main remaining reporting debt.
- **Employee↔User linkage is one-sided** (`users.linkedEmployeeId`, no index back, no integrity checks, no provisioning flow). Future employee accounts will need exactly this seam hardened.

Recommendation for next milestone (Section 50): **Organization Lifecycle & Relationship Normalization** — introduce employee status + dept/team mapping into org nodes before any new feature consumes them.

## 5. Current Role Model

Roles are **preset permission templates selected at user creation**, resolved by a single function:

- `getPermissionsForRole(role)` (`permissions.ts:428-436`) with presets: `ADMIN_PERMISSIONS` (:154 — every page edit+actions), `HR_PERMISSIONS` (:164), `MANAGER_PERMISSIONS` (:204), `QUALITY_PERMISSIONS` (:246), `DEFAULT_PERMISSIONS` (:287).
- Effective permissions merge chain: **role preset < position template < stored user override** inside `resolveEffectivePermissions`; scope-tier inheritance in `mergePermissionTier` (`permissions.ts:406-425`).
- Roles carry *authorization identity only*. A manager role does not imply managing anything until `OrgNode.managerUserId` names that user — explicitly documented ("Role and organizational assignment stay separate concepts", `permissions.ts:213-217`). This is the PART D separation, already largely achieved.

### Preset highlights

| Preset | Key grants | Scope doctrine |
|---|---|---|
| ADMIN | every page edit + actions | implicitly all |
| HR | workforce administration (employees CRUD+export) | `scope:'all'` (:171) — deliberate |
| MANAGER | read-mostly everywhere; approve requests/observations/months | `employees {level:'read', scope:'subtree'}` (:213) — reach = union of managed nodes ∪ own record |
| QUALITY | quality domain writes (observations/follow-ups/CAPA/complaints/KB) | `employees {read, scope:'all'}` (:253) |
| DEFAULT (user) | read-only generic pages | deliberately UNCONFIGURED → fail-closed `'own'` → empty set without link (:287-296) |

## 6. Current Permission Model

- Vocabulary: `PermissionLevel = 'none'|'read'|'edit'`; actions `create/update/delete/export/approve/upload/override` (`permissions.ts:3-8`).
- Carriers: `PagePermission { level, actions?, scope?, sections? }` — including section-level restriction inside a page (:60-78) and Control Panel persistence (`ControlPanelPage.tsx:359-379`).
- Page keys (~33 pages incl. overlay-only pages like `employee360`, `observationCategories`, plus `qualityDeductionsReport` mounted under the shared `reports` key, `permissions.ts:120-124`).
- Enforcement helpers: `verifyPermission(request, pageId, action?)`, `requireAuth`, `authenticateFromRequest` (`src/lib/verify-permission.ts:54-163`). Admin bypasses level checks but **not** scope checks on scoped routes. Denials: 401 (middleware presence)/403 (permission)/404-with-same-body (scope detail reads, anti-enumeration)/403 (scope creates/bulk).

## 7. Current Scope Model

Exactly one engine, two layers:

- **Pure engine** `resolveEmployeeScope(viewer, pageKey, permissions, inputs)` → `EmployeeScopeContext { scope, source, isUnrestricted, employeeIds:Set, includes(id) }` (`src/lib/scope/index.ts:113-179`).
- **Route guard layer** `src/lib/scope/server.ts` (`EMPLOYEE_SCOPE_PAGE_KEY='employees'`, `resolveEmployeeScopeFromDb`, `employeeInScope`, `linkedRecordInScope`, `filterRowsByEmployeeScope`, `filterEmployeesInScope`) — imported by **50 route files**; only `api/employees/route.ts:44-61` and `api/employee-360/[id]/route.ts:67-88` drive the raw engine directly (pinned by tests).
- Scope variants: `'all' | 'department' | 'team' | 'subtree' | 'assigned' | 'own'`.
- Resolution inputs: `users.linkedEmployeeId` (identity anchor) → `orgNodes` + `employees` full lists → graph math. Manager reach = union of node subtrees where `node.managerUserId === viewer.userId`; department/team = nearest typed ancestor subtree; own = linked id only (**empty set without a link**); assigned = **dead variant** (engine supports it; no production feeder exists — M0.4 §31.5).
- Performance: `'all'` fast path = 0 DB reads; scoped = 2 cached full-table reads (`TTL.MEDIUM` 15s, write-invalidated, `db.ts:20-25`); every request additionally pays 1 uncached `users/{id}` read (+1 `positions/{id}` if held).
- Fail-closed defaults everywhere: unknown scope → `'own'`; missing link → empty set; cycle members unreachable; missing orgNodeId → excluded from restricted scopes.

## 8. Department / Team Analysis

- The distinction **exists structurally** (distinct OrgNode types with Arabic labels, `organization/types.ts:22-32`), and team vs department scopes resolve differently (nearest typed ancestor).
- It does **not exist at the employee-record level**: `employee.department` is a display string that can silently diverge from the org tree after a move (by design, never rewritten) or after node renames. Team name isn't stored on employees at all.
- Two hard inconsistencies found:
  - Reports department selection filters by NAME string equality against `employee.department` (`src/lib/reports/scope.ts:80-97`) — request-narrowing only, after authorized-scope intersection (`reports/run/route.ts:61-100`), but it means report grouping follows the frozen text, not the tree.
  - Knowledge base hardcodes a fixed department enum `'operations'|'quality'|'hr'|'sales'|'it'|'finance'` (`types/index.ts:278`) that will not match dynamically named org nodes.
- Verdict: keep both (snapshot + orgNodeId) as today; add a *derived-and-refreshable* department/team projection service rather than rewriting history (Section 38).

## 9. Managerial Hierarchy Analysis

- The **only** manager relationship in the system is `OrgNode.managerUserId` (a USER id), single-valued, per node (`organization/types.ts:40-41` header states this emphatically). `resolveManagerChain(graph.ts:182-196)` walks this chain; depth capped by MAX_ORG_DEPTH.
- Supported today: direct manager of a node; multi-node management (union subtrees); manager-of-managers via parent chains; department head implicitly (manager of the department node).
- Not supported / absent: employee-level `managerId`; multiple managers on one node; temporary/deputy managers; dotted-line reporting; active-status check of the manager *inside the scope engine* (a suspended manager simply can't log in; a deleted manager's node contributes to nobody's scope — which is fail-closed-safe but silent).
- Minimum robust architecture recommendation (no code yet): retain `managerUserId` as the sole managerial edge; if deputy managers ever become a requirement, represent them as additional manager edges on the same node (ordered list with `kind: primary|deputy|temporary{from,to}`) rather than employee-side fields.

## 10. Employee ↔ User Relationship

- Link exists **exactly once, on the user side**: `users.linkedEmployeeId`, admin-assigned (`dashboard/users/route.ts:47` exposes it; `verify-permission.ts:86` resolves scope from it). Employees do **not** store `userId`; there is no employee→user index.
- Cardinality enforced as 1:1 by convention only — no unique-index check prevents two users linking to one employee (RTDB has no constraint mechanism).
- Position linkage is separate and unused: no user holds a `positionId` today (`positions.ts:17-18`).
- Future accounts-for-employees feasibility: YES, without forcing it — the pattern is already demonstrated by the notification router writing explicit `recipientUserIds` resolved from links (`notifications/routing.ts`, M10). What would be required (documented, not implemented): employee→user uniqueness validator, invite/provision flow, default fail-closed permission preset, and archival rules binding employee lifecycle to account suspension.

## 12. Denormalization Findings

Deliberate creation-time snapshots (historical-integrity friendly, all consistent with the M0.6 principle):

- `QualityObservation`: `employeeName`, `department`, `positionSnapshot` frozen at creation (`quality-kpi.ts:143-148`) — best-in-class example.
- `FollowUp`: `employeeName?`, `department`, `position`, `responsiblePersonName?`, `createdByName`.
- `CAPACase`: `employeeName?`, `assignedToName?`, `correctiveAssignedToName?`, `preventiveAssignedToName?`, `closedByName?`, timeline `performedByName?`.
- `HrDeduction.employeeName?`, `CustomerComplaint.employeeName?`, `AppNotification.employeeName/assignedToName`, `RuleExecutionLog.affectedEmployeeName`, `AutomationRule.createdByName`.
- Server join helper `getEmployeeMap()` (`db.ts:247`) provides id→{name,department,position,shiftStart} enrichment for list endpoints.

Risks: name edits propagate nowhere (acceptable — snapshots are declared historical); but *report row keys* must use `employeeId` while `employeeName` may only label rows. Verified report columns label by name while filtering/metrics key on `employeeId`/month.

## 13. Employee ID Consistency Audit

Every major domain stores `employeeId` as the association to employees (types verified in `types/index.ts`): attendance :48, requests :61, qualityDeductions :83, hrDeductions :97, travelDeals :115, followUps :140, CAPA (`employeeId|null` + `relatedEmployeeIds[]`), complaints (`employeeId|null`), observations (`employeeId` required), notifications (`employeeId|null`), biometrics, ruleExecutionLog (`affectedEmployeeId`).

Verdict: **canonical identity is already employeeId across domains.** Remaining debt:

- `validateEmployeeId` exists and is applied on create paths (e.g., complaints POST :113-115) but uniformity varies by route age.
- Some records tolerate `null` employee ids (CAPA, complaints) — legitimate but complicates aggregation-by-employee completeness accounting.
- Free-text `responsiblePerson` fields on follow-ups hold user-ish references whose format is unchecked.

Migration-debt list (for later phases, not now): none blocking; improvements are validators + null-handling conventions.

## 15. Employee 360 Readiness

Implemented endpoint `GET /api/employee-360/[id]` (413 lines) + SPA drawer (`Employee360Page.tsx`, `employee360/EmployeePerformanceSection.tsx`):

- Aggregates 9 sources via `Promise.allSettled` (attendance, biometrics, requests, qualityDeductions, hrDeductions, followUps, travelDeals, complaints, capaCases).
- IDOR-guarded by canonical scope; out-of-scope = identical 404 body (:83-86); sensitive-field gating via `resolveFieldAccess` (:347-350).
- Canonical metric reuse: risk via `computeRisk()`, CAPA overdue/effectiveness via `capaMetrics` (:8-15,184-201); healthScore = 100 − risk; rule-based Arabic recommendations (:323-333) — deterministic heuristics, correctly positioned below the future analytical layer.
- Gaps versus Part N target: deductions/attendance windows are **current-month only**; followUps/complaints/travel/CAPA are career-wide with **no time-scope parameterization**; **observations and KPI-history layers are absent** (no `qualityObservations`, no monthSnapshots/attendanceResults joining despite `time-scope` §G layering helpers existing for exactly this); no contextual initiation besides one `navigateTo('capa', …, {employeeId})` button; performance characteristics: 2× full getAll + 7 filtered queries per view.

Readiness verdict: strong foundation; a second-generation 360 should become a thin consumer of domain aggregators over the TimeScope contract rather than doing in-route filtering.

## 16. Contextual Actions Readiness

Backend seams (already real): `POST /complaints/[id]/create-capa`, `/follow-ups/[id]/escalate-capa`, `/hr-deductions/[id]/create-capa`, `/quality/[id]/create-capa`; automation rules can synthesize cross-domain records (`RuleAction.type` includes `create_follow_up`, `create_capa`, `escalate_case`, `update_employee_status`, `types/index.ts:361`).

Navigation/context infrastructure: `navigateTo(page, highlightId, params)` + global `openEmployee360(employeeId)` (`store.ts:20-45`) — cross-page context passing exists and is used by Notifications (`targetPage/actionUrl`) and one 360 button.

UI gaps: per-row "⋮ More" menus exist mainly in workflow-designer/control-panel; domain pages rely on explicit forms/dialogs; no standardized Smart Form mount that pre-fills from context params (complaint form takes `dealId` as free text instead of a picker resolved from nav context).

Verdict: the architecture can support contextual actions cleanly — what's missing is a front-end convention (form registry keyed by `{entityType, contextIds}`) and per-entity action-config (visibility by state/permission/scope), not new backend plumbing.

## 17. Deal Context Analysis

Current implementation (`TravelPage.tsx` 1572 lines + `travelDeals` type/route):

- Card displays rich service-status toggles (flight/hotel/visa/tours/transportation), destination, dates, dealer/customer names, notes, status pipeline `upcoming→in_progress→completed|canceled`.
- Actions: create/edit/delete, Excel/CSV upload import (`/api/travel/upload`), service status changes inline, tabs/expanders, client pagination.
- Reporting/export: row export exists via reports family; complaint-link from a deal card is **not present** (the inverse direction, complaint→dealId text field, exists).

Audit conclusion: the deal card is close to the "core information" ideal already; secondary actions belong under a per-row menu, and cross-domain creation hooks are the gap.

## 20. Current KPI Architecture

- **Canonical engines, not UI:** `lib/metrics/kpiMetrics.ts` (`computeEmployeeScore`, `computeMonthSnapshot`, `computeTrend`, `aggregateSnapshots`, `qualityToPerformanceFactor`), `capaMetrics.ts`, `followUpMetrics.ts`, `riskMetrics.ts` (`computeRisk` with breakdown), `lib/kpi-scoring/` (generic `PerformanceFactor`, `ScoreInput/Result` primitives), `lib/attendance/monthly-engine.ts` + `kpi.ts` (attendance factor adapter), `lib/hr-performance` (HR factor builder).
- **Config-driven behavior:** singleton `kpiSettings` doc (`DEFAULT_KPI_SETTINGS`: defaultScore 100, allowBonus maxBonus 20, approvalRequired, leaderboardEnabled, closeMonthLock, trendCalculation rollingAverage) — formulas read settings; management route `kpi-settings`.
- **Provenance contract:** `MetricResult` (metricId, employeeId, period, scope, value, calculationVersion, source) defined in time-scope §F for future consumers.
- Duplications found: risk weights live both in `lib/risk-weights.ts` and metric consumers referencing constants (single canonical `computeRisk` — acceptable); the legacy `/api/reports/generate` recomputes attendance-compliance-style columns adjacent to the canonical attendance engine (the known duplicate to retire); dashboards consume snapshots rather than recomputing (good).
- Score/trend direction deliberately owned by the Quality trend engine (`time-scope` §15 note); narrative labels pending business configuration where thresholds are heuristic (360 recommendations are rule placeholders — mark related scoring expectations as `pending_business_configuration`).

## 21. MTD KPI Readiness

- Attendance: **native MTD support** — `getEvaluatedDates(monthKey, asOf)` evaluates only days ≤ asOf within the month (`lib/attendance/dates.ts:80-108`); results regenerate mid-month.
- Quality: month snapshots compute from live observation lists, so invoking the canonical computation for the current month naturally yields month-to-date; the closed-month lock then freezes finals (`month-lock`, `closeMonthLock` setting). Hybrid semantics ("snapshot when closed, live otherwise") are already typed (`ReportDataMode='hybrid'`) though no hybrid runner ships yet.
- Dashboards/reports: range machinery is month-key based (`KpiRangePreset`, `resolveMonthsInRange`, `TimeScope`); true day-granularity within the running month is supported in raw-data reports (`date-range` mechanism) — so the Aug-1→Aug-24 requirement is expressible today without duplicating KPI logic by combining `date-range` for raw domains and `current_month` for snapshot domains.

## 25. Historical Reporting Analysis

## 35. Data Integrity Risks

Risk/debt register (identified, not remediated):

1. **Employees lack lifecycle status** — cannot deactivate; transfers and exits leave records fully in scope forever (HIGH).
2. One-way user↔employee link: no uniqueness validator, no dangling-check on `linkedEmployeeId`, no employee→user reverse index (MEDIUM-HIGH as usage grows).
3. Divergence drift: `employee.department` text vs renamed org nodes vs KnowledgeBase static enum → inconsistent grouping axes in reports (MEDIUM).
4. Mixed date formats: `DD/MM/YYYY` strings + substring matching (`findWhereContains('attendance','date','MM/YYYY')`, 360 route :95) vs ISO vs `YYYY-MM` keys — fragile, unindexable, year-ambiguity-prone (HIGH for reporting scale-up).
5. Orphan/unmapped employees (no orgNodeId) silently excluded from scoped views — safe-by-default, invisible loss risk operationally (MEDIUM; validator tooling would help).
6. Circular/quarantined nodes possible only via direct DB edits (move validates); archived parents accepted in engine subtrees (LOW-MEDIUM).
7. Duplicate-team/-dept detection: none exists (names non-unique) (LOW-MEDIUM).
8. Null-employee records (CAPA/complaints) reduce completeness of employee rollups (accepted behavior; surface in reports as "unassigned").
9. Pre-existing hygiene debts documented in milestone reports: tsc baseline errors (19), lint backlog (~11.8k), 1 known failing legacy test (`quality-migration`).

## 37. Performance Risks

Measured patterns: fetch-whole-table + in-memory predicate (ubiquitous), scope resolution 2×cached full-tables (fine ≤ a few thousand employees), uncached `users/{id}` per request, employee-360 issuing ~9 parallel calls incl. 3 unbounded getAll per profile view, client-side pagination over fetched arrays (TravelPage/ReportsPage/etc.), RTDB offers no multi-field indexes so server filters are O(table) per request — acceptable now, degraded later.

Mitigations ranked by value-over-cost (aligned with actual size, avoiding premature optimization):

1. Extend the month-snapshot/pre-aggregation precedent to deals/complaints/follow-ups monthly summaries.
2. Trim 360 fan-out to per-employee child-query collections.
3. Raise cache tiering on hot config tables.
4. Consider per-request memo of employees+orgNodes combined read (`getAllBatch` exists, db.ts:73).
5. Keep TimeScope-aware incremental aggregations as the long-term shape.
