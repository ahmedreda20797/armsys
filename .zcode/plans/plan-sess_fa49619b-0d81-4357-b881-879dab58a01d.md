### Part B — Enhance EmployeeSearchInput.tsx (edit existing, single source) — FUTURE-PROOF ARCHITECTURE
Generic identifier architecture — no field assumed mandatory; works today AND with future schema expansion with zero rewrite:
- Ordered candidate-field list SEARCH_FIELDS = ['name','email','code','department','position','mobile']. `email` is an OPTIONAL FUTURE field: included automatically when present on an employee, gracefully skipped when absent.
- The component's LOCAL Employee interface gains an explicit `email?: string | null` to document future support. This does NOT modify the canonical Employee type (src/types/index.ts) or the DB schema — purely the component's local view. (Compliance with "Do not modify the Employee database schema in Milestone 8.")
- Matching: employee matches the query (case-insensitive) if the query is a substring of ANY present (truthy) field in SEARCH_FIELDS. No field is assumed to exist.
- Never fake data: absent fields skipped entirely — no synthesized emails/codes.
- Suggestion display dynamically composes strongest available disambiguators: primary=name; secondary=department · position (when present); tertiary=email if present else code · mobile. Adapts per-employee to whatever real identifiers exist.
- Keyboard navigation: ArrowDown/ArrowUp activeIndex, Enter select, Escape close; aria-selected highlight.
- Selection contract unchanged: display value is presentation-only; onChange always resolves to the real employeeId.
- Preserve all props/variants so the 10 current consumers keep working. No duplicate component.
- Future schema expansion (e.g. adding email to canonical Employee type) requires zero changes to consuming pages or this component — picked up automatically. Nothing is named/structured in a way that assumes email does not exist.
