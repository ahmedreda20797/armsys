# M0.2.1 COMPLETION REPORT

Wave 2.1 — Authorization Surface Cleanup (Closing the Remaining Authorization Stragglers)
Date: 2026-08-23 · Scope: M0.2.1 ONLY (per approved M0 security roadmap)

---

## 1. Executive Summary

The three remaining auth-only GET read surfaces and the CAPA POST
actor-identity straggler identified by the M0.2 completion report
(§14.1 / §14.2) are closed. `GET /api/quality-observations`,
`GET /api/observation-categories`, and `GET /api/kpi-settings` now
enforce the full chain the frontend already enforces —
**authentication → effective permission → resource access** — each
gated by the EXISTING page permission key its sibling mutation gate
and its UI page consumer already use. `POST /api/capa-cases` now
derives its authoritative actor identity (`createdBy` /
`createdByName` and the `case_created` timeline event) from the
token-authenticated caller, never from `body.createdBy` /
`body.createdByName` — the exact pattern the M0.1 PUT fix
established for the same resource family.

No new permission keys were invented (all three gates reuse existing
`APP_PAGES` keys resolved through the single existing
`resolveEffectivePermissions` inside the existing `verifyPermission`
helper, admin bypass unchanged). No business logic, filtering,
seeding behavior, KPI engine, CAPA workflow, response schema, or UI
was modified. Employee 360 section permissions remain
foundation-only and untouched.

Verification: `tsc` and `lint` outputs are identical to the M0.2
baseline; the test suite grew from 897 to 936 tests (+39, all
passing) with the same single pre-existing failure
(`quality-migration.test.ts`). All 63 M0.1 and 59 M0.2 security
tests still pass. Zero regressions.

## 4. CAPA Actor Identity Fix

Before: the POST built its record and initial timeline event from
`body.createdBy || 'system'` and `body.createdByName || 'النظام'` —
a display-name forgery vector (creation itself was authenticated and
permission-gated, but the recorded creator was caller-chosen text).

After (mirrors the reviewed M0.1 PUT fix in
`capa-cases/[id]/route.ts` verbatim):

```ts
const actorUser = permCheck.user ? await getById('users', permCheck.user.id) : null;
const actorId   = permCheck.user?.id || 'system';
const actorName = actorUser?.name || actorUser?.email || 'النظام';
```

- `createdBy` / `createdByName` on the created record and
  `performedBy` / `performedByName` on the `case_created` timeline
  event now come from the authenticated caller.
- The `|| 'system'` fallbacks are defensive only — the route is
  unreachable without an authenticated `permCheck.user` because the
  `capa`/`create` gate runs first.
- AUTHENTICATED ACTOR IDENTITY vs BUSINESS/DISPLAY DATA: the client
  may still SEND `createdBy`/`createdByName` (CAPAQuickCreate sends
  its own session identity), but those fields carry no legitimate
  business meaning distinct from the creator, so they are simply
  ignored — nothing is deleted from the request contract and the
  response schema is unchanged.
- All other CAPA creators in the codebase (follow-ups escalate-capa,
  quality/complaints/hr-deductions create-capa, rules-engine) were
  audited: they ALREADY resolve the actor from `permCheck.user?.id`
  or hardcode `'system'` for engine-driven cases — no other
  body-derived actor existed (verified by grep: zero
  `body.createdBy` references remain under `src/app/api`).
- CAPA workflow behavior, timeline semantics, notifications, and
  capaId generation are untouched.

## 12. Frontend/Backend Parity

For each of the 3 GET routes, frontend visibility ↔ PageRouter/page
permission ↔ API permission now use the same effective permission
semantics — proven by the parity test (§8) over
`resolveEffectivePermissions` on both sides:

- **observations / observationCategories / kpiSettings**: the page
  components (`ObservationsPage`, `ObservationCategoriesPage`,
  `KpiSettingsPage`) check `usePermissions(key).canView`; the APIs
  now check `verifyPermission(request, key, 'view')`. No UI change
  was needed — no genuine mismatch was found.
- **Multi-consumer endpoints analyzed (documented, not worked
  around — same fail-closed policy M0.2 established):**
  - `/api/observation-categories` also feeds KpiDashboardPage and
    EmployeeQualityKpiPanel as display enrichment (category
    name/color maps only). The `hr` preset holds `kpiDashboard:
    read` but `observationCategories: none`, so those auxiliary
    labels degrade to their fallback rendering for HR. Intentional:
    HR was explicitly denied observation-category data, and every
    surface where categories are operationally required
    (observations create/filter, templates, categories management)
    requires a preset that also grants `observationCategories ≥
    read` (manager edit, quality read).
  - `/api/quality-observations` also feeds the Employee 360 quality
    panel's observation list. `hr`/generic-`user` presets hold
    `observations: none`, so the list degrades to its empty state —
    the exact degradation M0.2 already accepted for the same panel
    (`kpiDashboard: none` for generic users). Full Employee-360
    section gating remains explicitly deferred.
- CAPA creation UI: `CAPAQuickCreate` sends its own session identity
  as `createdBy`; the server now derives the same value from the
  token — identical outcome for honest clients, forgery impossible
  for dishonest ones.
