# M0.1 COMPLETION REPORT

Wave 1 — Critical Unauthenticated Endpoint Remediation
Date: 2026-08-22 · Scope: M0.1 ONLY (per approved M0 Security Audit)

---

## 1. Executive Summary

All 10 endpoint vulnerabilities assigned to M0.1 are closed. Every
critical route now rejects unauthenticated callers (401), dummy/forged
Bearer tokens (401 — the middleware only checks header presence, the
handlers now verify the JWT signature), and authenticated callers
without the required page/action permission (403). The
`x-internal-scheduler` authentication bypass was replaced by a
server-side `CRON_SECRET` (timing-safe, fail-closed, no fallback
secret), the `reports/capa` un-awaited `requireAuth` bug is fixed, the
public health endpoint no longer leaks user identities or scans the
users table, and the `firebase/test` SSRF primitive is admin-gated and
locked to official Firebase RTDB hosts (it has a legitimate consumer —
the Firebase settings page — so it was secured, not deleted).

Actor identity in touched routes is now derived from the authenticated
token, never from body fields. Two static regression guards were added
so the classes of bugs fixed here (missing auth in a route file;
un-awaited auth call) cannot silently return. No business logic,
formulas, or KPI engines were modified.

Verification: `tsc` and `lint` outputs are byte-identical to the
pre-M0.1 baseline; the test suite grew from 769 to 832 tests with the
same single pre-existing failure. Zero regressions.

## 7. Authentication Decisions

- **401 vs 403**: handlers call `await requireAuth()` first (missing /
  dummy / tampered token → 401), then `verifyPermission()` (insufficient
  permission → 403). This distinction matters because the middleware
  only checks Bearer presence — `Authorization: Bearer x` reaches
  handlers and must be rejected there. Tests pin this exact case.
- **JWT verification**: unchanged (`jose` HS256, issuer `arm-erp`,
  access-token type check, user re-fetched from db with suspension and
  effective-permission resolution) — no new auth architecture.
- **CRON_SECRET**: compared timing-safely; requests presenting it as a
  Bearer token are scheduler calls, anything else falls through to
  normal JWT auth (a raw secret is not a valid JWT, so the paths are
  unambiguous). When `CRON_SECRET` is unset, cron access fails closed
  on both routes. The hardcoded `'internal-cron-token'` fallback is
  gone. Vercel Cron automatically sends
  `Authorization: Bearer $CRON_SECRET` to `/api/cron/*`, matching this
  scheme (vercel.json already registers the path).
- **Actor identity**: `rules` POST and `capa-cases/[id]` PUT derive
  `createdById/createdByName` and `performedBy/performedByName` from the
  authenticated caller (with a users-table lookup for the display
  name); body-supplied identity fields are ignored (asserted by test
  with a forged `createdById`).

## 8. Tests Added (63)

Per endpoint: no header → 401; `Bearer x` → 401; tampered-signature
token → 401; insufficient role → 403; authorized role → success path
(uploads run a real in-memory xlsx end-to-end; rules POST asserts the
forged actor is ignored). Admin bypass is exercised via the success
paths. Specific extras:

- capa-sla: old `x-internal-scheduler` header alone → 401; wrong secret
  → 401; correct secret → 200; user token → 200.
- cron/capa-sla-check: no/wrong secret → 401 with zero downstream
  fetches; correct secret → forwards `Bearer <secret>` and NOT the old
  header (fetch stubbed and inspected).
- firebase/test: 8 SSRF targets (localhost, plain http, private IP,
  arbitrary host, suffix-spoofed host, credentials, custom port,
  garbage) → 400 with **no outbound request**; official RTDB URL →
  success.
- health: response contains none of `firstUser/email/role/usersCount`;
  no `getAll('users')` call; db-down → 500.
- Regression guards: (a) every `route.ts` under `src/app/api` must
  contain an auth primitive or be explicitly allowlisted — allowlist is
  exactly `auth/login`, `auth/refresh`, `health` (each with a reason;
  stale entries also fail); (b) no route may call
  `requireAuth`/`verifyPermission`/`authenticateRequest*` without
  `await` (comments stripped so commented-out auth can't pass).

## 11. Known Limitations

- `capa-cases/[id]` enforces page-level authorization only, per audit
  instruction; record-level organization scope is explicitly deferred.
- `capa-sla` remains callable by ANY authenticated user (pre-M0.1
  behavior preserved deliberately); the scheduler path is what was
  hardened.
- The middleware still checks Bearer presence only (JWT verification in
  middleware is an M0.2+ item); handlers are now the authoritative
  verifiers, which the new tests enforce.
- Security tests stub the db layer (in-memory), so they exercise
  authorization logic, not Firebase I/O.
- `CRON_SECRET` must be set in the deployment environment; until it is,
  scheduled SLA checks fail closed by design (logged loudly on the cron
  route).
