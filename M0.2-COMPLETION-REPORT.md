## 1. Executive Summary

All 8 M0.2 target endpoint groups (9 route handlers) now enforce the
full authorization chain the frontend already enforces:
**authentication → effective permission resolution → page/action
permission → resource access**. Every target route previously
authenticated the caller but granted access on token possession
alone; each now additionally requires the existing page permission
that represents the same business capability its UI consumer checks
(`visiblePages` ↔ PageRouter ↔ API).

No new permission keys were invented — all 9 gates reuse existing
`APP_PAGES` permission keys resolved through the single existing
resolver (`resolveEffectivePermissions`) inside the existing
`verifyPermission` helper, with the existing admin bypass unchanged.
The highest-impact fix: `POST /api/firebase/sync` (full-database
synchronization) was triggerable by ANY authenticated user and is
now effectively admin-only, matching its admin-only settings page.
`GET /api/employees` now requires the `employees` view permission —
zero impact on stock roles since every preset already grants
`employees ≥ read`; the Milestone-10 data-scope engine in that route
is untouched (M0.3 remains deferred).

A latent flakiness bug was found in the shared security test harness
(`tamperToken` mutated the final base64url character of the JWT
signature, which carries 2 don't-care padding bits — some flips
decode to the SAME MAC and the "tampered" token stays valid ~6% of
runs). It is a test-infra bug only (the flipped credential is
byte-identical after decode, so it is not an attack vector); fixed
to mutate the first signature character, whose bits are always
significant. M0.1's 63 security tests were re-run and still pass.

Verification: `tsc` and `lint` outputs are byte-identical to the
M0.1.1 baseline; the test suite grew from 838 to 897 tests (+59,
all passing) with the same single pre-existing failure
(`quality-migration.test.ts`). Zero regressions. No business logic,
formulas, KPI engines, snapshots, rule execution, or UI were
modified.

## 8. Authorization Changes

Pattern applied to all 9 handlers (identical to the M0.1
established pattern, e.g. `rules` POST):

```
await requireAuth(request)            → 401 when missing / dummy /
                                        tampered token (JWT verified
                                        in-handler; middleware
                                        presence-check is not trusted)
await verifyPermission(request, KEY, 'view')
                                      → 403 when the EFFECTIVE level
                                        for KEY is 'none'
admin role                            → allowed (existing bypass,
                                        unchanged, inside
                                        verifyPermission)
```

- Effective permission resolution is the SINGLE existing resolver:
  role preset → position template → stored per-user overrides
  (`resolveEffectivePermissions`), consumed by
  `authenticateFromRequest`. An explicit stored `'none'` overrides a
  role grant; a stored grant overrides a role deny; a missing stored
  key falls back to the preset. No second resolver was created
  (enforced by a new guard).
- Error semantics: 401 vs 403 distinction maintained per file idiom
  (`api-error` helpers for the KPI family, `NextResponse.json` for
  the rest). No permission internals are leaked in responses.
- No caller-supplied `userId`/`role` is consulted for these
  decisions (authorization uses the token-authenticated identity);
  no actor-identity code paths were changed in M0.2 routes.
- `GET /api/employees`: the Milestone-10 data-scope engine
  (`resolvePageScope` / `filterEmployeesByScope`) and the sensitive
  field stripping are untouched — organization scoping remains
  inert/deferred to M0.3. M0.2 answers only "may this caller use
  this capability?".

## 9. Tests Added (59)

`src/lib/__tests__/m02-security-alignment.test.ts` (55):

- Full matrix per endpoint (A no header → 401; B dummy Bearer → 401;
  C tampered signature → 401; D role with permission `none` → 403;
  E read-level role → 200; F edit-level role → 200; G admin → 200
  via bypass) with real seeded rows asserted in the 200 bodies.
- firebase/sync: admin reaches the Firebase layer — in the test env
  Firebase is deliberately unconfigured, so the deterministic
  past-the-gate response is 503 (asserted `never 401/403`); D-cases
  prove non-admins are stopped BEFORE any sync work.
- Stored-permission regression (the original frontend/backend
  inconsistency): quality role + stored `riskCenter:'none'` → 403
  (stored 'none' beats role grant); hr role + stored
  `riskCenter:'read'` → allowed (stored grant beats role deny);
  missing stored key falls back to the preset (not to 'none').
- Frontend/backend parity regression: for all 6 M0.2 page keys × 9
  role/stored-override cases, `verifyPermission(view).allowed` must
  equal the frontend `canView` semantics computed from the SAME
  `resolveEffectivePermissions` map that `AuthContext` builds
  (admin short-circuits on both sides).

`src/lib/__tests__/m02-route-permission-regression.test.ts` (4
static guards over `src/app/api/**/route.ts`, comments stripped):

1. **M0.2 gate pin** — each of the 9 routes must keep
   `verifyPermission(request, '<agreed key>', 'view')`; the gate
   cannot be silently dropped or repointed at a broader key.
2. **No invented permission keys** — every page key passed to
   `verifyPermission` in ANY route must exist in `APP_PAGES`
   (prevents scattered permission strings).
3. **Single permission resolver** — only
   `src/config/permissions.ts` may define
   `resolveEffectivePermissions` / `getPermissionsForRole`.
4. **No caller-supplied identity trust** — no route may compare a
   request-body role to 'admin', or assign a body `userId` into an
   actor/createdBy/performedBy identity (narrow regexes; legitimate
   db-record/token-role comparisons are not flagged).

Guards 1–2 of the M0.1 file (auth coverage + await discipline)
remain in force and continue to pass.

## 12. Frontend/Backend Parity Results

Per M0.2 page: `visiblePages` ↔ PageRouter ↔ API authorization now
use the same effective permission model:

- **kpiDashboard / monthClose / kpiSettings / rulesEngine / rules /
  firebase / riskCenter / employees**: the page component (or the
  router) checks `usePermissions(key).canView`; the API now checks
  `verifyPermission(request, key, 'view')`. Both derive from
  `resolveEffectivePermissions` — proven by the parity test (§9).
- **Multi-consumer endpoints analyzed:**
  - `/api/risk-center` also feeds the Operations Center (AOCC)
    widget. In every stock preset, `operationsCenter ≥ read`
    co-occurs with `riskCenter ≥ read` (hr has neither), so no
    stock role breaks. A custom stored override granting
    `operationsCenter` while denying `riskCenter` now makes the
    widget fail closed with its existing error state — intentional:
    the user was explicitly denied risk data, and showing it in an
    operations widget would leak it. Documented, not worked around.
  - `/api/kpi-dashboard` + `/api/month-snapshots` also feed the
    Employee 360 "quality" tab (`EmployeeQualityKpiPanel`). The
    generic `user` preset has `employee360: read` but
    `kpiDashboard: none`, so that panel now degrades to its
    zero/empty state for generic users. This matches the preset
    authors' documented intent ("management pages are NOT part of
    the generic default role"; HR/manager/quality all hold
    `kpiDashboard: read`). Full Employee-360 section gating is
    explicitly out of M0.2 scope.
  - `/api/employees` feeds pickers on many pages; since every stock
    preset grants `employees ≥ read`, no visible page loses data.
