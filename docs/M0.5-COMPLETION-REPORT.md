## 1. Executive Summary

M0.5 closes the read-side authorization gap. Before this milestone, a
user holding a page's view permission could READ every record on that
page regardless of organizational scope — the M0.3/M0.4 scope engine
guarded employee lists, employee detail, and write paths, but list
endpoints, detail endpoints, dashboards, aggregates, and exports
returned workforce-wide data.

After M0.5, **every employee-linked read response is intersected with
the caller's authorized employee scope at the server-side retrieval
boundary** — before search, filters, sorting, pagination, counting, and
serialization. 25 route files adopted the canonical stack; 65 new
integration tests (categories A–K) pin the behavior; the full suite is
**1111 tests / 1110 passing / 1 pre-existing failure**; `tsc` and lint
remain at their pre-milestone baselines.

## 2. Milestone Objective & Core Principle

> A user must not be able to READ employee-linked data that is outside
> their authorized organizational scope.

Applies to: list endpoints, detail endpoints, dashboards,
employee-derived aggregates, search endpoints, filters, report data
selection, employee-linked resources, and exports.

## 3. Non-Negotiable Architecture Compliance

- **No new scope engine.** The canonical engine
  (`src/lib/scope` → `resolvePageScope` + `resolveEmployeeScope`) is the
  single membership authority. M0.5 adds only thin adoption helpers in
  `src/lib/scope/server.ts`.
- **No route-specific role checks.** Every route resolves scope the
  same way: `resolveEmployeeScopeFromDb(viewer, 'employees', permissions)`.
- **No client-side authorization.** All filtering happens server-side
  before serialization; client filtering is UX only.
- **One consumption layer.** The M0.3/M0.4 invariant "routes consume
  the engine only through `@/lib/scope/server`" is preserved — the new
  `filterEmployeesInScope` wrapper keeps aggregate routes on the server
  guard module, and the existing m03/m04 invariant tests pass unchanged.

## 4. The M0.5 Read-Scope Doctrine

- Scope applied at the **retrieval boundary**: `AUTHORIZED_SCOPE ∩
  FILTER`, never filter-then-scope. A query parameter can only NARROW.
- The **stored record is the authorization relationship**: rows are
  scoped on their STORED `employeeId` (and CAPA `relatedEmployeeIds`),
  never on client-supplied values.
- **Anti-enumeration**: an out-of-scope detail resolves with the SAME
  404 body as an unknown record.
- **Employee-mandatory tables fail closed** on rows without a
  resolvable employee link; optionally-linked records (complaints,
  CAPA) follow the M0.4 optional-link rule.
- **Separation of concerns**: M0.5 changes WHICH records are visible —
  never business formulas, deduction rules, scoring, or approval flows.

## 8. Canonical read-scope helpers (`src/lib/scope/server.ts`)

- `authScopeViewer(auth)` — adapts `requireAuth`'s `AuthenticatedCaller`
  to `ScopeViewer` (M0.4 routes use `asScopeViewer(permCheck.user)`; the
  two adapters serve the two caller shapes).
- `RowScopeOptions { optionalLink?, relatedEmployeeIdsField? }`.
- `linkedRecordInScope(record, ctx, options)` — single-record decision
  for detail routes (mandatory links fail closed; optional links pass
  when unlinked; `relatedEmployeeIds` must ALL be in scope).
- `filterRowsByEmployeeScope(rows, ctx, options)` — list-route row
  filter; no-op for unrestricted viewers.
- `filterEmployeesInScope(employees, ctx)` — employee-ARRAY wrapper over
  the canonical `filterEmployeesByScope` for aggregate routes; keeps the
  "one consumption layer" architecture invariant intact.

## 9. List endpoint adoption (10 routes)

Every list GET resolves the scope ONCE per request immediately after
the table read, then filters rows before any domain logic. Enrichment
(`withEmployee`/`withEmployeeFull`) runs AFTER the filter, so name
lookups only ever touch authorized rows. Tab counts, month lists,
urgent-trip lists, risk aggregates, and pagination totals (travel,
follow-ups, capa-cases) all derive from the authorized dataset.

## 10. Detail endpoint adoption + anti-enumeration

`capa-cases/[id]` and `quality-observations/[id]` resolve scope after
lookup and before serialization; out-of-scope records return the SAME
404 body as unknown ids (pinned byte-for-byte by tests B1/B4). Evidence
nested inside an observation travels with its parent — scoping the
parent scopes the evidence.

## 11. Search / filter / pagination ordering guarantee

Tests C1–C6 pin: capa free-text search runs on the authorized set
(searching an out-of-scope title yields 0); `employeeId` query filters
cannot widen scope; pagination `total` equals the authorized count;
observation month/employee filters intersect with scope. Source-order
static checks (K3) enforce scope-before-filter structurally in four
representative routes.

## 12. Optional-link rule (complaints, CAPA)

Unlinked complaints/CAPA are organizational records — visible on
permission alone. Any PRESENT link must be in scope. Applied uniformly
in: complaints list, capa list, capa detail, risk-center factor tables,
reports/capa, reports/capa-export, complaints create-capa.

## 13. relatedEmployeeIds rule

A CAPA is visible only when its `employeeId` AND every id in
`relatedEmployeeIds` is in scope. Tests G1–G3 pin: mixed-link case
hidden from list, 404 on detail with the same body as unknown,
all-links-in-scope case visible. The same rule feeds risk-center and
both CAPA report/export routes.

## 14. Dashboard — home/stats

Single scope boundary right after the 8-table batch load: `employees`
via `filterEmployeesInScope`; attendance, requests, travelDeals,
qualityDeductions, biometrics, followUps via `filterRowsByEmployeeScope`;
`deductionRules` (no employee link) untouched. Every reported metric —
totalEmployees, today's attendance, department stats, pending requests,
travel, late employees, monthly performance, top offenders, quality
summary, biometric stats, follow-up summaries — derives from authorized
rows only (tests D1–D3, including a deep no-leaked-names scan).

## 15. Dashboard — risk-center

Risk rows exist only for in-scope employees; every factor table
(attendance, quality, HR, follow-ups, complaints, CAPA) is intersected
first, with complaints/CAPA under the optional-link + related-ids
rules so a per-employee breakdown only counts cases the viewer could
open. Summary counts, level buckets, and department analysis derive
from the scoped population. The risk formula itself is untouched
(tests D4–D5).

## 16. Dashboard — kpi-dashboard (route + service)

`DashboardFilters.authorizedEmployeeIds` carries the caller's set into
`getKpiDashboard`. `restrictSnapshotToEmployees` restricts
`employeeScores` and REBUILDS every employee-derived aggregate
(`departmentScores`, `categoryTotals`, `approvalStats`) from authorized
entries — the frozen per-employee fields carry all rebuild inputs, so
no unscoped statistic survives and no KPI value is recomputed.
Authorization runs BEFORE the cosmetic department/employeeId filters
(AUTHORIZED_SCOPE ∩ FILTER; a department filter can never bypass
scope — test D8). `avgApprovalHours` (a month-wide timestamp average
not attributable per employee) reports the neutral 0 when restricted.
Unrestricted viewers pass `null` — the service skips restriction
entirely (tests D6–D8).

## 17. Dashboard — month-snapshots/[id]

`scopeMonthSnapshotToEmployees` restricts the full snapshot: employee
scores restricted, aggregates rebuilt, frozen top/bottom leaderboards
filtered, and every archived `snapshotHistory` version restricted
identically. Stored per-employee values (including month-wide rank)
are shown AS STORED on surviving rows — the M0.4 row-filter precedent.
Admin receives the frozen snapshot byte-for-byte (tests D9–D10).

## 18. Reports — generate

The employees array is intersected with scope before any row is built;
rows, the global summary, and meta totals describe authorized
employees only. Per-employee factor maps are keyed lookups, so
out-of-scope entries are never read. The canonical attendance engine
and quality/HR composition are untouched (tests E1–E2).

## 19. Reports — capa aggregate

All eight sections (summary, byDepartment, byEmployee, monthlyTrends,
byStatus, byPriority, byCategory, bySource) aggregate only authorized
cases under the optional-link + related-ids rules, applied before the
query-param filters. The `غير معرّف` bucket aggregates unlinked
organizational cases and remains visible (tests E3–E4).

## 20. Reports — capa-export

An export is a list response with a different serializer: the streamed
file contains exactly the rows the CAPA list would show — scope before
enrichment and before body filters (test E5 verifies the CSV text;
scope assertions run on the same code path as the xlsx branch).

## 21. Reports — export (posted rows re-verified SERVER-side)

The client posts rows for rendering; the file is still a read
response, so the SERVER decides which employees may appear: posted
rows are intersected with the caller's scope (rows without a
resolvable employeeId are dropped fail-closed) and every total in the
file is recomputed from the surviving rows — the posted summary object
is never trusted (tests E6–E7 parse the produced xlsx).

## 22. M0.4 gap remediation — derived CAPA creations (4 routes)

`follow-ups/[id]/escalate-capa`, `complaints/[id]/create-capa`,
`quality/[id]/create-capa`, `hr-deductions/[id]/create-capa` create
CAPAs carrying a STORED employeeId without a scope check. Each now
verifies the stored target against the caller's scope BEFORE creating
anything (optional-link rule for complaints; mandatory fail-closed for
the rest); out-of-scope resolves as the same 404 body as an unknown
record (tests J3–J8).

## 23. M0.4 gap remediation — travel/upload

The spreadsheet import writes deals for sheet-matched employees AND
creates new employee records — its output cannot be confined to a
restricted set. It now demands `hasUnrestrictedEmployeeScope` (the
canonical bulk-write rule) and answers 403 to scoped viewers
(tests J1–J2).

## 24. Fail-closed doctrine

Viewers without a configured employees scope (default `user` role,
custom users without scope entries, unbound managers) resolve to an
EMPTY authorized set: lists return [], dashboards report zero
employees, detail lookups 404, unlinked organizational records remain
visible on permission. Tests H1–H4 (and D3) pin the behavior.

## 25. Unrestricted fast path & performance

Admin/HR/Quality ('all') short-circuit inside the canonical engine
with ZERO additional DB reads — test I1 proves no `orgNodes` read
occurs (employees reads observed post-scope are name enrichment).
Scoped viewers add exactly two cached (`TTL.MEDIUM`) reads
(orgNodes + employees) per request, shared by every adopted route via
`resolveEmployeeScopeFromDb`. Scope resolution happens once per
request; row filters are O(n) in-memory passes.

## 26. Data flow requirements compliance

authenticate → (page view permission where the page defines one) →
resolveEmployeeScope → AUTHORIZED_SCOPE ∩ FILTER → search/filter/sort/
paginate/count → enrich → serialize. No route computes a count, total,
ranking, or aggregate before the scope intersection.

## 27. Caching considerations

The db layer's 15s TTL cache is BEHIND the boundary: scope filtering
runs per-request on cached reads, so a scope change applies on the
next request without cache poisoning. Snapshot restriction produces
shallow copies — frozen documents are never mutated.

## 28. Separation of concerns — no business-logic changes

No deduction rule, KPI formula, risk weight, approval flow, ranking
algorithm, or export layout changed. The only functional edits inside
domain code are the two defensive fixes in §29.
