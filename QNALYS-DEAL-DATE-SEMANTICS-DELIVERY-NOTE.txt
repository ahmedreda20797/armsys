CANONICAL CONTRACT (§DEAL-DATES)
--------------------------------
One shared semantic layer — src/lib/deal-dates.ts — is now the ONLY
place that decides which date a deal-derived metric is counted by:

  CREATED → createdAt      record creation / intake activity
  CLOSED  → closedAt       observed successful completion
                           (closed deals, sales productivity)
  TRAVEL  → departureDate  the customer's travel date
                           (travel operations, travel volume)

In Qnalys the deal entity IS the travel deal (collection
'travelDeals'): departureDate is the travelDate dimension and a
deal "closes" when its status transitions to 'completed'.

closedAt LEDGER (introduced — §14 compliant)
--------------------------------------------
TravelDeal.closedAt (ISO, optional) is stamped ONLY by the server:
  • PUT /api/travel/[id] — entering 'completed' stamps the observed
    moment; leaving 'completed' clears it; staying 'completed'
    keeps the stored value verbatim.
  • Client-supplied closedAt is always stripped (never trusted).
  • POST create + Excel upload → closedAt = null. A created-as-
    completed record or a sheet row has NO trustworthy closure
    timestamp, so it stays UNKNOWN — never fabricated.
  • HISTORICAL DATA LIMITATION: every completed deal that predates
    this change has closedAt = null. Its closure month is
    UNKNOWABLE and is surfaced as "unknown" — it is NOT counted in
    any month and NOT derived from its departure date. Going
    forward, every new completion transition is stamped.

PERIOD ATTRIBUTION — NO HIDDEN FALLBACK
---------------------------------------
Old behavior (performance-intelligence/loaders.ts):
  deal month = departureDate ?? createdAt   ← mixed dimensions
  (a deal with no departure date silently became a "createdAt"
  deal; a completed deal's "completion" was really its departure
  month).
New behavior — three explicit, independently-tested functions:
  monthOfDealTravel  → TRAVEL (departureDate; missing → unattributed)
  monthOfDealClosed  → CLOSED (closedAt; missing → UNKNOWN)
  monthOfDealCreated → CREATED (createdAt)
A missing date is NEVER replaced by another dimension's date.

CANONICAL DATE MAPPING (metric → meaning → date)
------------------------------------------------
  closedDeals / closedTotal (period)   → successful completions → closedAt
  closedMonthly (window series)        → observed closures       → closedAt
  closedUnknownMonth                   → completions w/o closedAt → UNKNOWN (surfaced)
  travelTotal (period) / monthly       → customer travel volume   → departureDate
  byStatus / active / canceled         → operational snapshot     → status (not period-attributed)
  completionRate                       → status snapshot share    → status (among travel-period deals)
  evidenceRecordMonth('travelDeals')   → evidence grouping        → departureDate (via canonical helper)
  upcoming/urgent travel (home, AOCC,
  travel page, travel-status lib)      → travel operations        → departureDate (unchanged)
  unseen/polling counters              → record activity          → createdAt (unchanged)
  KPI QUALITY ENGINE                   → contains NO deal-derived component (verified) — formula untouched
  monthSnapshots/yearSnapshots closedAt → month-close audit timestamps — a DIFFERENT domain concept, untouched

HISTORICAL-DATA LIMITATION
--------------------------
  All pre-existing 'completed' travel deals lack a closure timestamp.
  Their closed-month attribution is UNKNOWN (explicitly surfaced as
  'مكتملة بتاريخ إغلاق غير محدد' in HR/smart-report/360) and they are
  never counted in any month nor derived from travel dates. From this
  release onward, every completion transition stamps a truthful
  server-side closedAt, so closed-deal period history accrues
  naturally from live data.
