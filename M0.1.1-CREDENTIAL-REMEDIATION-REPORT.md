Security follow-up to M0.1. Scope: exposed-credential investigation, removal,
rotation guidance, and verification only. No other architecture touched.

> No secret values appear in this report. Credentials are identified by
> redacted fingerprints (SHA-256 prefix) only.

## 1. Exposure Status

The file contained a full PEM-format Firebase service-account private key and
a Firebase web API key. Every Firebase value in `.env.example` was
byte-for-byte identical (matching SHA-256 fingerprints) to the live values in
the local `.env` used by the running application — i.e. the example file was
seeded from the real working credentials, not placeholders.

## 10. Rotation Required

**YES — treat the service-account private key and (defensively) the API key
as compromised** and rotate manually. Identifying values (project ID, app ID,
sender ID, URLs) do not require rotation.

Rationale: the private key and API key sat in a file whose purpose is to be
shared/committed. Even though Git never received it, any copy of this
workspace, backup, sync, or archive may contain it.

## 11. Manual Rotation Steps (for the project owner)

Service-account private key (primary):

1. Open Firebase Console → Project settings → Service accounts.
2. Find the service account matching the exposed client email
   (`…firebase-adminsdk…@…iam.gserviceaccount.com`) → manage in
   Google Cloud Console → IAM & Admin → Service Accounts.
3. Generate a **new key** (JSON). Store it in your secret manager only —
   never in `.env.example` or any repo file.
4. Update the deployment platform's environment variables (e.g. Vercel →
   Project → Settings → Environment Variables): `FIREBASE_PRIVATE_KEY`
   (and confirm `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PROJECT_ID`,
   `FIREBASE_DATABASE_URL`, `FIREBASE_STORAGE_BUCKET`).
5. Update the local `.env` with the new key.
6. **Delete the old exposed key** in Service Accounts (Keys tab) — this
   invalidates every copy, including the pre-remediation `.env.example`,
   the `.firebase/…/functions/.env` copy, and the dev-cache copy (§15).
7. Redeploy and verify: app boots, `/api/health` (authorized) reports
   Firebase configured, and an authenticated write/read round-trip works.

Firebase web API key (defensive — see §15 notes on its threat model):

1. Firebase Console → Project settings → General → Web API key.
2. Google Cloud Console → APIs & Services → Credentials: create a new
   browser-key with HTTP-referrer restrictions, then restrict the old key
   (or delete it once the new one is deployed everywhere
   `FIREBASE_API_KEY`/client config is used, including the in-app Settings
   page configuration).
3. Update env vars + redeploy as above.

   - `.firebase/arm-erp-project/functions/.env` (auto-generated from `.env`

   it is consumed by Firebase hosting/frameworks tooling and the in-app
   Settings-page client config. Firebase web API keys are public identifiers
   by design, but restriction (§11) is recommended defense-in-depth.
